# Community Pulse

**라이브: https://comm.power-worker.com**

공개 접근이 가능한 커뮤니티 게시판을 **30분마다 수집**해, **유사한 제목의 글을 하나의 그룹으로 묶고**, **조회수+댓글수 기준 TOP 3**를 스냅샷으로 **누적 기록**하는 정적 대시보드.

수집기는 GitHub Actions cron 이 실행하고, 결과 JSON 을 저장소에 커밋한다. 프론트엔드는 빌드 없는 정적 HTML/CSS/JS 로 그 JSON 을 읽어 렌더한다. **외부 npm 의존성이 없다.**

---

## 수집 대상과 지표 제공 범위

**이 프로젝트에서 가장 먼저 알아야 할 사실: 소스마다 제공하는 지표가 다르다.**

| 커뮤니티 | id | 조회수 | 댓글수 |
|---|---|---|---|
| 루리웹 베스트 | `ruliweb` | ✅ | ✅ |
| 인스티즈 | `instiz` | ✅ | ✅ |
| 더쿠 핫게 | `theqoo` | ✅ | ✅ |
| 클리앙 모두의공원 | `clien` | ✅ | ✅ |
| 인벤 오픈이슈갤 | `inven` | ✅ | ✅ |
| 뽐뿌 자유게시판 | `ppomppu` | ✅ | ✅ *(euc-kr)* |
| 웃긴대학 베스트 | `humoruniv` | ✅ | ✅ *(euc-kr)* |
| 디시 주식갤 | `dc_stock` | ✅ | ✅ |
| 디시 부동산갤 | `dc_realestate` | ✅ | ✅ |

총 9곳. 현재 **모든 소스가 조회수·댓글수를 제공한다**(루리웹은 `td.hit`·`td.time` 을 제공하는데 초기 조사에서 잘못 판단해 `views: null` 로 두었던 것을 바로잡았다).

- **없는 값은 만들어내지 않는다.** 목록에서 얻을 수 없는 지표는 `null` 로 저장하고, UI 카드에 "조회수 미제공" 경고를 표시한다.
- 따라서 **조회수를 제공하는 소스와 그렇지 않은 소스가 같은 순위표에서 경쟁하면 순위가 왜곡된다.** 각 카드의 `scoreBasis` 배지를 보고 해석해야 한다.

**제외한 곳**
- 로그인이나 JS 렌더가 필요: 네이버카페(부동산스터디·월부), 블라인드, 토스증권, 호갱노노
- **robots.txt 가 목록 경로를 `Disallow`**: SLR클럽 자유게시판, MLBPARK, 네이트판 — 응답은 200 이지만 규칙을 지켜 넣지 않는다
- **봇 UA 에 406 응답**(UA 게이팅): 보배드림
- **GitHub Actions 러너 IP 에서 차단**: 에펨코리아(HTTP 430), 오늘의유머(403), 아카라이브(403). 로컬(가정용 IP)에서는 200 이 오지만 Actions 에서만 반복 실패한다. 브라우저 UA 위장은 하지 않기로 했으므로 뺐다. 파서 파일은 남아 있고 `collector/sources/index.js` 의 `DISABLED_SOURCES` 에 이유가 적혀 있다 — 셀프호스티드 러너를 쓰면 되돌릴 수 있다
- **서버 렌더 목록에 조회수·댓글수가 없음**: 개드립 — `data-document-srl` 은 있지만 제목만 있는 위젯형 목록이라 지표를 얻을 수 없다. 지표 없이 넣으면 점수 0 이 되어 순위에 의미가 없으므로 제외했다
- **네이버 종토방**: robots.txt 는 `Allow: /item/board.naver?code=*` 로 허용하지만, 서버가 브라우저 아닌 User-Agent 에 200 응답으로 오류 페이지(약 2.7KB)를 돌려주며 게이팅한다. 브라우저를 위장하지 않기로 했으므로 수집 대상에서 제외했다. (`collector/sources/naverStock.js` 및 `isBlocked` 훅 제거)

## 수집 매너

- robots.txt 를 확인하고 허용 경로만 요청한다.
  - 에펨코리아: `Disallow: /` 이지만 `Allow: /best` → 베스트 목록만
  - 디시: 차단 갤러리 목록에 `neostock`·`immovables` 없음
  - 오늘의유머: `User-agent: * → Allow: /`. 단 **Content-Signal: `search=yes, ai-train=no, use=reference`** 를 선언한다 — 제목을 인용하고 원문으로 링크하는 이 용도는 `use=reference` 에 해당하며, 학습 데이터로 쓰지 않는다
  - 더쿠: robots.txt 가 404(규칙 없음)
  - 클리앙·아카라이브·뽐뿌: `User-agent: *` 가 해당 목록 경로를 Allow
  - 인벤·웃긴대학: 해당 경로에 금지 규칙 없음
- **목록 페이지만 요청한다.** 개별 글은 요청하지 않고 링크로만 노출한다.
- 정직한 User-Agent 를 쓴다: `community-pulse-bot/1.0 (+https://github.com/liveforfun/community-pulse)`
- 소스를 **순차 처리**하고 요청 사이 **1.5초** 지연을 둔다. 동시 요청하지 않는다.

## 유사글 그룹핑

제목을 정규화한 뒤 **문자 bigram 자카드 유사도**로 묶는다. 외부 API·의존성을 쓰지 않는다.

정규화 단계 (`collector/cluster.js`):
1. 파일 확장자 접미사 제거 (`.jpg`, `.mp4` …)
2. 선행 말머리 제거 (`[유머]`, `(스포)`)
3. 자모 반복 감탄사 제거 (`ㅋㅋㅋ`, `ㄷㄷ`, `ㅠㅠ`)
4. 한글·영문·숫자만 남기고 이모지·특수문자 제거
5. 불용어 제거 후 **공백 전부 제거** (한국어 띄어쓰기가 불안정해 문자 n-gram 이 더 안정적)

**임계값 `SIMILARITY_THRESHOLD = 0.38`** — 실데이터로 조정한 값이다.

| 근거 | 값 |
|---|---|
| 에펨 "종편 아나운서가 반포 신축 50억 아파트 입주권 산 비결" ↔ 루리웹 "종편 아나운서가 50억 반포자이 아파트를 산 비결" | 유사도 **0.448** |

같은 이슈인 위 쌍이 초기값 0.45 에서 아깝게 탈락했다. 표현 차이가 더 큰 동일 이슈는 그보다 낮게 나오므로 0.38 로 낮췄다. 0.25 까지 내려도 최대 묶임이 5건(같은 제목 연속 게시글)에 머물러 과병합 징후는 없었으나, 서로 다른 주제가 뭉칠 위험을 피해 0.38 로 둔다.

**커뮤니티 경계를 넘어 비교한다** — 같은 이슈가 여러 커뮤니티에 퍼진 경우를 묶는 것이 목적이므로 소속 커뮤니티는 판정에 쓰지 않는다.

> 실제 관찰: 초기 5곳은 주제 영역(유머 / 게임 / 주식 / 부동산)이 거의 겹치지 않아 커뮤니티 교차 그룹이 드물었다. **주제가 겹치는 오늘의유머·더쿠를 추가하자 곧바로 교차 그룹이 생겼다** — 예: "ㅈㄴ 심각해서 궁금한이야기Y까지 나온 최근 청소년 유행"이 인스티즈·더쿠에서 동시에 화제로 잡혔고 합산 점수로 1위가 됐다. 교차 그룹을 더 늘리려면 주제가 겹치는 소스를 더 붙이면 된다.

## 점수 — 누적값이 아니라 **30분 증가분**

```
score = (deltaViews ?? 0) + (deltaComments ?? 0) × 100
deltaX = 이번 스냅샷의 X − 직전 스냅샷의 같은 글(URL 기준)의 X
```

**왜 증분인가.** 조회수·댓글수는 작성 이후 누적값이다. 그대로 순위를 매기면 오래된 글이 구조적으로 이긴다 — 실제로 누적 방식에서는 **10시간 전에 쓰인 글이 2위**였고, 30분 창 안에 작성된 글은 전체의 21%뿐이었다. 증분으로 바꾸면 "지금 뜨거워지고 있는 글"이 올라온다.

`deltaBasis` 가 증분의 근거를 밝힌다:

| 값 | 의미 |
|---|---|
| `measured` | 직전 스냅샷에 같은 글이 있어 실제 증가분을 쟀다 (가장 정확) |
| `new-in-window` | 이번에 처음 보였고 **작성시각이 창 안**이다 → 누적값 전부가 이 창에서 생긴 것 |
| `first-seen` | 이번에 처음 보였는데 작성시각이 창 밖이거나 불명 → 증가분을 알 수 없다(`null`) |

증분을 하나도 잴 수 없으면(첫 실행 등) 누적값으로 대체하고 스냅샷의 `scoreMode` 를 `cumulative-fallback` 으로 기록한다. UI 도 그 사실을 표시한다.

### 수집 간격이 30분이 아닐 때 — 30분 환산

증분은 "30분치"가 아니라 "**직전 수집 이후**치"다. GitHub Actions 예약 실행은 건너뛰어지므로 실제 간격이 벌어진다 — 2026-07-27 하루 관측치는 59분~**235분**, 42회 예상 중 12회만 실행됐다.

그대로 두면 두 가지가 깨진다.

1. **슬롯 간 비교** — 간격이 벌어진 슬롯일수록 점수가 통째로 부풀어, 7일 종합에서 "그날 가장 오래 끊겼던 슬롯"이 이긴다.
2. **슬롯 안 비교** — `measured`(간격 전체치)가 `new-in-window`(최대 30분치)를 구조적으로 이긴다. 210분 간격에서 실측 7,000·70 글과 창내신규 500·5 글의 점수 차는 14배인데, 그중 7배는 창 길이 차이일 뿐이다.

그래서 **실측 증가분을 실제 경과시간으로 나눠 30분치로 환산**해 순위에 쓴다.

```
factor = 30 / elapsedMinutes          # elapsedMinutes = 이번 capturedAt − 직전 capturedAt
deltaViewsNorm = round(deltaViews × factor)      # deltaBasis === 'measured' 에만 적용
score = (deltaViewsNorm ?? 0) + (deltaCommentsNorm ?? 0) × 100
```

**`new-in-window` 는 환산하지 않는다.** 글의 생애 전체가 창(30분) 안에 있어 누적값 자체가 이미 30분 이하의 값이다. 여기에 `30/경과분`을 곱하면 실제로 겪은 시간보다 짧은 시간으로 나누는 셈이라 값이 근거 없이 줄어든다. `first-seen` 은 원값이 `null` 이라 해당 없다.

**원값은 덮어쓰지 않는다.** `deltaViews`/`deltaComments` 는 잰 그대로 남고, 환산값은 `deltaViewsNorm`/`deltaCommentsNorm` 에 따로 담긴다. 스냅샷 원본은 7일간 보관되며 재집계에 쓰이므로 측정치 자체를 잃으면 안 된다.

환산하지 않는 경우는 스냅샷에 이유를 남긴다:

| `deltaNormalization.reason` | 조건 |
|---|---|
| `ok` | 환산 적용 |
| `no-previous` | 비교 대상 없음 (첫 실행 등) |
| `invalid-elapsed` | 경과시간이 0 이하 (시계 문제·중복 실행) |
| `gap-too-large` | 24시간 넘게 끊김 — 하루치를 48로 나눈 값은 그 시간대의 화제성을 대표하지 못한다 |

스냅샷 최상위에 `elapsedMinutes`(실제 경과분)와 `deltaNormalization {applied, reason, factor, slotMinutes, appliedTo}` 가 기록된다. UI 는 간격이 예정치에서 20% 넘게 벗어나면 상단 라벨을 "30분 **환산** 증가분 기준"으로 바꾸고, 카드 지표 라벨과 소스 상태판에 실제 경과시간을 밝힌다. 필드가 없는 옛 스냅샷은 원값으로 대체해 그대로 읽힌다.

**주의**: 점수 체계가 누적 → 증분으로 바뀌었기 때문에, 7일 종합·일별 요약은 `scoreMode === 'delta'` 인 스냅샷만 후보로 삼는다(`legacySnapshotCount` 에 제외 개수를 기록). 두 방식은 스케일이 완전히 달라 섞으면 구버전이 순위를 독점한다.

댓글 1건을 조회 100회로 환산한다. 추천수는 수집·보관하지만 점수에는 넣지 않는다.

## 작성시간 정규화

사이트마다 표기가 제각각이라 `collector/time.js` 가 절대 시각(ISO)으로 통일한다. 이게 없으면 "이 창에 쓰인 글인가"를 판단할 수 없다.

| 원문 형태 | 예 | precision |
|---|---|---|
| 완전한 타임스탬프 | `2026-07-26 22:19:46` | `minute` |
| 두 자리 연도 + 시각 | `26.07.27 00:04:11` (뽐뿌) | `minute` |
| 월일 + 시각 | `07.26 22:23` (인스티즈) | `minute` |
| 시각만 | `00:03` (루리웹·인벤) → 오늘. 수집 시각보다 미래면 어제로 보정 | `minute` |
| 날짜만 | `07.26` (더쿠의 지난 글) | **`day`** — 시각 불명이라 창 판정에 쓰지 않는다 |
| 상대 시각 | `3 분 전` | `minute` |

`precision: 'day'` 인 글은 시각을 00:00 으로 두므로 "N분 전" 으로 표시하면 안 된다.

`scoreBasis` 는 어떤 지표로 점수를 냈는지 기록하며, UI 가 이를 그대로 표시한다:

| 값 | 의미 | UI 경고 |
|---|---|---|
| `views+comments` | 모든 글이 두 지표 보유 | 없음 |
| `comments-only` | 조회수 전무 | "조회수 미제공 — 댓글수만으로 산출" |
| `views-only` | 댓글수 전무 | "댓글수 미제공 — 조회수만으로 산출" |
| `partial` | 그룹 안에 제공/미제공 소스가 섞임 | "일부 글의 지표가 미제공 — 합산값이 불완전" |

## 누적 정책 — 원본 7일 + 일별 요약 영구 보존

스냅샷은 덮어쓰지 않고 슬롯별로 쌓인다. 이력은 두 단계로 보관한다.

| 단계 | 경로 | 보관 | 내용 |
|---|---|---|---|
| 30분 단위 원본 | `data/snapshots/<날짜>/<HHmm>.json` | **7일** | 수집한 글 전부(제목·URL·조회수·댓글수)와 전체 클러스터 |
| 일별 요약 | `data/daily/<날짜>.json` | **영구** | 그날의 TOP 3(원문 링크 포함) + 슬롯 목록 + 소스별 집계 |

30분 주기면 하루 48개 파일이 쌓인다. 원본을 영구 보관하면 1년에 17,500개 파일·커밋이 되어 저장소와 Actions 체크아웃이 무거워지므로, 7일이 지난 원본은 삭제하고 하루치를 요약 한 파일로 압축해 영구 보관한다.

**삭제 순서가 보장된다.** `collector/snapshot.js` 의 `prune()` 은 **해당 날짜의 일별 요약이 존재할 때만** 원본을 삭제한다. 롤업이 없으면 원본을 남기고 다음 실행에서 재시도하므로, 롤업 실패로 이력이 사라지는 일은 없다.

일별 요약 생성 규칙 (`collector/rollup.js`):
- **완료된 날만** 대상이다. 오늘은 아직 수집이 진행 중이라 만들지 않는다.
- 이미 요약이 있는 날은 다시 만들지 않는다(멱등).
- 그날의 TOP 3 는 TOP 3 만 훑는 게 아니라 **모든 슬롯의 전체 클러스터를 후보로** 삼는다. 같은 글이 여러 슬롯에 등장하므로 정규화된 제목으로 중복을 합치고 **최고 점수를 기록한 시점(`peakSlot`)** 을 남긴다.
- 요약에도 **원문 링크가 보존된다.** 다만 그날 수집한 글 전체 목록은 남지 않는다(TOP 3 만) — 용량 통제를 위한 의도된 손실이다.

전체 글까지 영구 보존이 필요하면 `RETENTION_DAYS` 를 늘리거나 별도 DB 로 옮겨야 한다.

일별 요약 스키마:
```json
{
  "date": "2026-07-20", "kind": "daily",
  "snapshotCount": 48,
  "firstCapturedAt": "…", "lastCapturedAt": "…",
  "itemCountTotal": 7968,
  "top": [ { "rank": 1, "title": "…", "score": 108180, "peakSlot": "2026-07-20T21:30+09:00",
             "totalViews": 73580, "totalComments": 346, "scoreBasis": "views+comments",
             "memberCount": 1, "communities": ["instiz"], "items": [ { "url": "https://…" } ] } ],
  "slots": [ { "slot": "…", "top1": "…", "itemCount": 166, "okSources": 5, "totalSources": 5 } ],
  "sourceSummary": [ { "id": "fmkorea", "name": "에펨코리아", "okCount": 47,
                       "emptyCount": 1, "blockedCount": 0, "errorCount": 0, "itemCountTotal": 1081 } ]

```

UI 의 "누적 수집 이력" 섹션은 30분 단위 원본과 일별 요약을 구분해 보여주며, 상단 "수집 시점" 선택기에도 두 그룹이 나뉘어 표시된다.

각 행은 두 영역이다. **본문(시각·1위 제목)을 누르면 그 1위 그룹 대표 글의 원문이 새 탭에서 열리고**, 오른쪽 아이콘 버튼을 누르면 기존처럼 그 시점 순위를 불러온다. 제목만 보여주고 갈 곳이 없으면 이력을 훑는 의미가 반감되므로 원문 이동을 기본 동작으로 뒀다. 링크는 인덱스의 `top1Url`(30분 원본)과 `days[].top1Url`(일별 요약)에서 온다 — 클러스터의 `items` 는 증분순이라 `items[0]` 이 곧 표시된 제목의 출처다. 링크가 없는 항목(수집 결과가 없던 슬롯, 보관 기간이 지나 원본이 삭제된 옛 인덱스 항목)은 밑줄·커서 없이 그대로 표시된다.

### 화면 배치

순위 카드가 화면 위쪽을 차지하도록 배치했다: 필터 → 순위 카드 → 키워드 → 누적 이력 → **소스 수집 현황판(최하단)**.

순위 카드의 총조회수·총댓글수·점수와 **지표 결손 경고(`scoreBasis`)** 는 `<details>` 로 **접혀 있고 클릭하면 펼쳐진다**(JS 없이 동작하며 키보드·스크린리더에서도 열린다). 접힌 요약줄에는 점수를 남겨 순위 근거를 잃지 않게 하고, 경고가 있는 카드는 요약줄에 작은 경고 아이콘을 띄워 펼칠 이유가 보이게 했다.

카드 상단에 커뮤니티 태그가 이미 있으므로 **"묶인 글" 목록에는 커뮤니티 이름·조회수·댓글수를 넣지 않는다** — 제목과 원문 링크만 둔다. 글 단위 지표는 30분 스냅샷 원본 JSON 에 그대로 남아 있다.

## 보기 종류 — 기본은 7일 종합 TOP 10

상단 "수집 시점" 콤보에서 세 가지 데이터셋을 고를 수 있다. **페이지를 열면 7일 종합 TOP 10 이 기본으로 표시된다.**

| 보기 | 데이터 | 순위 | 후보 |
|---|---|---|---|
| **7일 종합** (기본) | `data/weekly.json` | **TOP 10** | 7일간 전체 클러스터 |
| 30분 단위 원본 | `data/snapshots/…` | TOP 3 | 그 시점 클러스터 |
| 일별 요약 | `data/daily/…` | TOP 3 | 그날 TOP 3 |

7일 종합(`collector/weekly.js`)은 창 안의 모든 스냅샷의 **전체 클러스터**를 후보로 삼는다. 같은 글이 여러 슬롯에 반복 등장하므로 정규화된 제목으로 중복을 합치고 **최고 점수를 찍은 시점(`peakSlot`)** 을 카드에 표시한다.

주의: 보관 기간(7일)을 넘겨 30분 원본이 삭제된 날은 일별 요약을 쓰는데, 요약에는 그날 TOP 3 만 남아 있어 **후보가 3개로 줄어든다.** 그런 날이 있으면 소스 상태 패널에 경고를 띄운다(`partialDays`). 창과 보관 기간이 모두 7일인 현재 설정에서는 발생하지 않는다.

헤더의 수집 시각·카운트다운은 어떤 보기를 보고 있든 **항상 최신 스냅샷 기준**이다("수집이 얼마나 최신인가"를 알리는 정보이므로).

### 커뮤니티 필터는 커뮤니티별 순위를 따로 계산한다

기간 종합(7일·일별)은 파일에 전체 TOP N 만 담는다. 프론트에서 **그 TOP N 을 걸러내면 상위권에 글이 적은 커뮤니티는 결과가 0~3개로 쪼그라든다.** 초기 구현이 이 버그를 냈다(전체 TOP 10 중 루리웹 글이 없어 루리웹 선택 시 0개).

그래서 수집기가 후보 전체에서 **커뮤니티별 TOP N 을 따로 뽑아** `byCommunity` 에 저장한다. 프론트는 커뮤니티가 선택되면 `clusters` 대신 `byCommunity[id]` 를 쓴다. 30분 스냅샷은 전체 클러스터를 들고 있어 직접 걸러도 정확하므로 기존 경로를 유지한다.

## 7일 키워드 노출량

전 커뮤니티 제목에서 키워드를 뽑아 최근 7일치를 집계하고, 노출량이 큰 키워드가 크게 보이는 워드클라우드로 표시한다. 결과는 `data/keywords.json` 에 저장된다.

**노출량(exposure)의 정의** — 이 값을 오해하면 안 된다.

> (스냅샷 × 그 스냅샷에서 해당 키워드를 포함한 글) 의 합.

같은 글이 48개 슬롯에 계속 걸려 있으면 48로 계산된다. **게시판에 얼마나 오래·널리 걸려 있었는지**를 나타내는 값이며 **고유 글 수가 아니다.** 이 정의는 `keywords.json` 의 `exposureDefinition` 필드에 함께 실려 UI 각주에 그대로 표시된다.

`slots` 는 해당 키워드가 등장한 스냅샷 수, `communities` 는 커뮤니티별 등장 횟수다.

### 토큰화의 한계

**형태소 분석기를 쓰지 않는다**(외부 의존성 0 원칙). 따라서 정확한 명사 추출이 아니라 "제목에 자주 등장한 표현" 수준이다.

- 파일 확장자·자모 반복(`ㅋㅋㅋ`)·특수문자 제거 후 공백 분리
- 조사를 보수적으로 제거(`에서/으로/까지/은/는/이/가/…`). 떼고 남는 길이가 2자 이상일 때만 적용
- 2자 미만·12자 초과·순수 숫자·자모 조각 제외. **영문/숫자 토큰은 3자 이상만**(`vs`, `ai`, `tv` 같은 노이즈 제거)
- 불용어 목록으로 활용형·관형어를 걸러낸다(`이상`, `다른`, `했다`, `오늘자` …)

활용형이 완벽히 정규화되지는 않는다(`여자`와 `여자들`이 별개 키워드로 잡힌다). 정확도를 더 올리려면 형태소 분석기가 필요하고, 그건 외부 의존성 도입 결정이다.

### 집계 창과 원본 보관의 관계

`collector/keywords.js` 의 `WINDOW_DAYS`(기본 7)는 `snapshot.js` 의 `RETENTION_DAYS`(기본 7)와 **별개 상수**다.

| 관계 | 동작 |
|---|---|
| 창 ≤ 보관 기간 | 전부 30분 단위 원본에서 집계 (현재 상태) |
| 창 > 보관 기간 | 보관 기간을 넘긴 날은 **일별 요약의 `keywords`** 에서 집계 |

그래서 `WINDOW_DAYS` 를 30으로 올리기만 하면 원본이 7일치만 남아 있어도 30일 키워드가 이어진다. 각 스냅샷과 일별 요약이 자기 키워드 집계를 들고 있기 때문이다(집계 시 336개 원본을 다시 토큰화하지 않는다).

### 시각화

세 가지 보기를 제공한다. 워드클라우드는 값을 정확히 비교하기 어려운 형태이므로 **정확한 비교용 막대 보기와 표 보기를 함께 넣었다.**

| 보기 | 용도 |
|---|---|
| 클라우드 | 전체 분포를 한눈에. 글자 크기(면적 ∝ 값, 제곱근 스케일)와 색이 **같은 값**을 중복 인코딩 |
| 막대 | 상위 20개 정확한 비교. 단일 색, 길이로만 비교 |
| 표 | 전체 120개. 노출량·등장 슬롯·커뮤니티 분포 |

구현 메모:
- 외부 라이브러리 없이 **아르키메데스 나선 배치 + AABB 충돌 검사**로 배치한다. 텍스트 폭은 canvas `measureText` 로 실측한다.
- 커뮤니티를 색으로 구분하지 **않는다.** 흩뿌려진 마크는 모든 색 쌍이 동시에 비교되는데, 5색은 색약 분리 기준(CVD ΔE ≥ 8)을 통과하지 못한다. 커뮤니티는 툴팁과 표에서 텍스트로 제공한다.
- 색 램프는 단일 블루 hue 의 명도 5단계(`#cde2fb → #1c5cab`)이며, 다크 표면(`#101622`) 기준으로 검증기 전 항목 PASS(단조 명도, 단계 간격 ≥0.06, 밝은 끝 2.73:1, hue 폭 3°).
- 컨테이너에 들어가는 만큼만 배치하고, **표시된 개수와 남은 개수를 각주에 밝힌다** — 조용히 누락시키지 않는다. 전체는 표 보기에서 확인.
- **반응형 파라미터**(실측 배치율로 조정):
  - 높이: 폭 <560px → 660, <1100px → 520, 그 이상 → 360. 좁을수록 세로로 면적을 확보한다.
  - 최대 글자 크기: `width / 9` (28~54px). 54px 고정이면 폭 390px 화면에서 긴 한글 단어가 컨테이너보다 넓어져 통째로 버려졌다.
  - 컨테이너보다 넓은 단어는 버리지 않고 들어갈 때까지 2px 단위로 줄인다.
  - 결과: 폭 360px 34개 → **71개**, 390px 35개 → **74개**(약 2배). 768px 이상은 118~120개 전부 표시.
- 리사이즈 시 200ms 디바운스로 재배치. 렌더 약 56ms.

## 자동 수집 설정

`.github/workflows/collect.yml` 이 30분마다 실행되고 `data/` 변경을 커밋·푸시한다.

**저장소 설정 필요**: Settings → Actions → General → Workflow permissions 를 **Read and write permissions** 로 바꿔야 푸시가 된다.

**cron 은 `7,37 * * * *` 다 — `*/30` 이 아니다.** `*/30` 은 매시 :00·:30 에 걸리는데, 이 두 분은 전 세계 워크플로가 몰리는 시각이라 GitHub 스케줄 큐에서 계속 밀린다. 실제로 `*/30` 으로 돌린 2026-07-27 하루 동안 42회 예상 중 **12회만 실행**됐고 낮에는 3.5시간까지 벌어졌다(실행된 12회는 전부 성공 — 실패가 아니라 스킵이었다). 혼잡하지 않은 분으로 옮기면 체감이 크게 나아진다. 다만 GitHub 은 어떤 cron 도 실행을 보장하지 않으므로, **간격이 벌어져도 순위가 깨지지 않도록 점수를 30분치로 환산**한다(위 "수집 간격이 30분이 아닐 때" 참고).

주의사항:
- GitHub Actions 예약 실행은 부하에 따라 **수 분 지연되거나 건너뛰어진다.** 정확히 30분 간격이 보장되지 않으므로, UI 는 약속된 주기가 아니라 스냅샷에 기록된 실제 `capturedAt` 을 표시한다.
- 간격이 계속 벌어져 문제가 되면 GitHub cron 을 버리고 외부 스케줄러(Vercel Cron 등)에서 `workflow_dispatch` 를 호출하는 쪽이 확실하다. 이 경우 `workflow` 스코프가 있는 토큰이 필요하다.
- 전 소스가 실패해도 스냅샷은 남긴다. "언제 어느 파서가 깨졌는지"가 그 자체로 데이터다.

## 파서가 깨졌을 때

정규식 HTML 파싱이므로 사이트 개편에 취약하다. 소스별로 실패가 격리되어 한 곳이 깨져도 나머지는 수집된다.

증상별 대응:

| 스냅샷 상태 | 의미 | 대응 |
|---|---|---|
| `empty` | 요청은 200 인데 행이 0건 | 해당 `sources/*.js` 의 `ROW_RE` 부터 확인 |
| `blocked` | 403/429 또는 UA 게이팅 | 우회하지 말 것. 소스 제외를 검토 |
| `error` | 타임아웃·네트워크 실패 | 일시적일 수 있음. 다음 슬롯 확인 |

파서 수정 시 주의: **태그 내부에 탭·줄바꿈이 섞인다.** `<li class="…">` 처럼 공백을 고정한 정규식은 조용히 0건을 반환한다. `<li\b[^>]*class="[^"]*…"` 형태로 공백에 관대하게 쓴다. (실제로 이 함정 때문에 초기 구현에서 에펨·루리웹·인스티즈가 부분 실패했다.)

또한 **에펨코리아는 User-Agent 에 따라 두 가지 템플릿을 내려준다** — 제목 링크가 `/best/{id}` 인 형태와 `/index.php?…&document_srl={id}` 인 형태. 파서는 양쪽을 모두 처리한다.

**인코딩**: 소스 모듈에 `encoding: 'euc-kr'` 을 선언하면 `http.js` 가 `TextDecoder` 로 디코딩한다(Node 16 은 full-icu 포함). 선언하지 않으면 UTF-8.

**중첩 컨테이너·클래스 접두사 함정.** 아카라이브는 행이 `<div class="vrow hybrid">` 인데 내부에 `vrow-inner`·`vrow-top`·`vrow-bottom`·`vrow-preview` 가 있다. `class="vrow[^"]*"` 로 매칭하면 내부 div 까지 잡혀 행 슬라이스가 65자로 잘리고 **조회수가 전부 null 이 된다.** `class="vrow(?:\s[^"]*)?"` 처럼 단어 단위로 매칭해야 한다. 클리앙·웃긴대학도 중첩 태그 때문에 닫는 태그를 맞출 수 없어 **시작 마커로 경계를 자르는 방식**을 쓴다.

**공지 행은 반드시 걸러야 한다.** 인벤 공지는 조회수가 수년간 누적되어 180만이라, 걸러내지 않으면 공지 3건이 TOP 3 를 영구히 점령한다(실제로 그렇게 됐다). 사이트별 공지 표식: 인벤 `tr.notice`·`span.notice-icon`, 더쿠 `tr.notice`/`td.no` 가 숫자 아님, 디시 `data-type="icon_notice"`, 나머지는 조회수 칸이 비어 있는 것으로 판별한다.

**속성값 따옴표도 사이트마다 다르다.** 오늘의유머는 `class='list_memo_count_span'` 처럼 작은따옴표를 쓴다. 큰따옴표만 보는 정규식은 오류 없이 조용히 0 을 반환하므로(실제로 댓글수가 전부 0 으로 수집되는 버그가 났다), `class=['\"]…['\"]` 형태로 양쪽을 허용해야 한다. 새 파서를 붙인 뒤에는 **특정 지표가 전부 0/ null 로만 나오는지 반드시 확인할 것.**

## 확장

새 소스를 추가하려면 `collector/sources/` 에 아래 형태의 모듈을 만들고 `sources/index.js` 에 등록한다.

```js
module.exports = {
    id: 'my_source',
    name: '표시 이름',
    url: 'https://example.com/board',
    provides: { views: true, comments: true },   // 실제 제공 여부를 정직하게 적을 것
    parse(html) {
        return [{ title, url, author, views, comments, recommends, postedAt }];
        // 얻을 수 없는 지표는 null. 추정값을 넣지 말 것
    },
    isBlocked(html) { return false; }            // 선택 — UA 게이팅 감지
};
```

프론트엔드 `app.js` 의 `COMMUNITY_CONFIG` 에도 같은 `id` 로 표시 이름·색을 추가한다.
